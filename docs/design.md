# Notification Gateway 设计文档

> 本文档为 RightCapital AI Coding 作业的架构设计文档，聚焦问题理解、整体架构、关键工程决策与系统边界，不包含具体技术实现细节（如类定义、数据库表结构、代码实现等）。

---

## 1. 问题理解

企业内部多个业务系统在关键事件发生时，需要调用外部系统供应商提供的 HTTP(S) API 进行通知。典型场景包括：

- 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统；
- 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态；
- 用户购买商品后，通知库存系统进行库存变更。

这些外部供应商的 API 在请求地址、Header、Body 格式上各不相同；而内部业务系统只关心“通知请求能够被稳定、可靠地送达”，并不关心外部 API 的具体返回值。

因此，本系统的核心职责是：

> **接收内部业务系统提交的外部 HTTP 通知请求，并尽可能可靠地将其投递到目标供应商地址。**

本质上，这是一个**带持久化和重试能力的出站 HTTP 通知投递服务**（Outbound Notification Gateway）。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **可靠投递** | 通知一旦被接受，就必须被持久化，并在各种失败场景下持续重试，直到成功或进入死信。 |
| **异步解耦** | 接收接口不等待 vendor 响应，立即返回“已接受”，避免 vendor 延迟/故障影响内部系统。 |
| **多供应商支持** | 不同 vendor 的 URL、Method、Header、Body 格式通过配置化方式管理，支持快速接入。 |
| **可观测性** | 每条通知有清晰的生命周期状态，失败、死信、队列堆积等情况可被监控和告警。 |
| **边界清晰** | 明确本系统解决什么问题、不解决什么问题，避免过度设计。 |

---

## 3. 核心概念

| 概念 | 说明 |
|------|------|
| **Notification Request** | 业务系统提交的“请通知某 vendor”的请求，包含 vendor 标识、业务 payload、幂等键等。 |
| **Vendor Config** | 每个外部供应商的配置，包括 endpoint、HTTP method、headers、body 模板、超时、重试策略、限流等。 |
| **Delivery Worker** | 负责从待投递队列中取出请求，组装 HTTP 请求并发送给 vendor 的执行单元。 |
| **DLQ（Dead Letter Queue）** | 超过最大重试次数仍未成功的通知进入的死信队列，需人工介入后重放。 |
| **Idempotency Key** | 业务方提供的幂等键，用于本系统去重和透传给 vendor。 |

## 4. 系统边界

### 4.1 本系统解决的问题 ✅

1. **接收并持久化通知请求**：提供 HTTP API 接收业务系统请求，写入持久化存储后返回“已接受”。
2. **按 vendor 路由与格式化**：根据 `vendorKey` 查找配置，将业务 payload 转换为 vendor 要求的 HTTP 请求格式。
3. **异步可靠投递**：通过 worker 异步发送 HTTP 请求，失败时按策略重试。
4. **幂等控制**：维护幂等键与最终投递状态的映射，避免已成功的通知被重复投递。
5. **死信处理**：超过最大重试次数的通知进入 DLQ，支持人工重放。
6. **按 vendor 限流**：保护下游 vendor 不被突发流量压垮。
7. **降级与熔断**：vendor 长期不可用时，减少无效投递尝试，避免资源浪费。
8. **并发控制**：多 worker / 多实例环境下，避免同一条通知被并行处理。
9. **崩溃与重启恢复**：服务重启后，能自动恢复未完成的投递任务。
10. **基础可观测性**：记录通知生命周期、暴露队列状态与 DLQ 指标。

### 4.2 本系统明确不解决的问题 ❌

| 问题 | 不解决的原因 |
|------|-------------|
| **Vendor 返回值的业务处理** | 需求明确业务系统不关心外部 API 返回值，本系统只记录投递成功/失败。 |
| **Vendor 侧的 exact-once 保证** | 跨系统 HTTP 场景下无法经济地实现 exactly-once；本系统只提供幂等键透传，vendor 是否去重由 vendor 决定。 |
| **企业级密钥管理（KMS/Vault）** | 第一版仅做简单配置；vault 集成是后续演进项。 |
| **多租户、多 Region** | 当前需求未涉及，避免过早引入复杂度。 |
| **复杂工作流编排 / Saga** | 这不是通知系统的职责范围。 |
| **实时流式处理** | DB 队列足以满足 MVP 的可靠性和吞吐量要求。 |
| **SLA 赔偿或补偿事务** | 本系统保证“尽力可靠投递”，不承诺业务层面的 SLA 赔偿。 |

## 5. 整体架构

### 5.1 架构概览

本系统采用**“接收即持久化、异步投递、状态机驱动”**的架构：

```text
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────┐
│  业务系统        │────▶│  Notification API    │────▶│  持久化存储      │
│  (注册/支付等)   │     │  接收 & 校验          │     │  通知请求队列    │
└─────────────────┘     └──────────────────────┘     └─────────────────┘
                                                               │
                                                               ▼
                                               ┌─────────────────────────────┐
                                               │   待投递队列（按状态 + 时间调度） │
                                               └─────────────────────────────┘
                                                               │
                              ┌────────────────────────────────┼────────────────────────────────┐
                              ▼                                ▼                                ▼
                    ┌──────────────────┐           ┌──────────────────┐           ┌──────────────────┐
                    │   Scheduler      │           │   Scheduler      │           │   Scheduler      │
                    │   拉取待投递      │           │   重试调度        │           │   死信/归档       │
                    └──────────────────┘           └──────────────────┘           └──────────────────┘
                              │                                │                                │
                              ▼                                ▼                                ▼
                    ┌──────────────────┐           ┌──────────────────┐           ┌──────────────────┐
                    │   HTTP Client    │──────────▶│   Vendor APIs    │           │   DLQ / 告警     │
                    │   发送请求        │           │   外部供应商      │           │   人工重放       │
                    └──────────────────┘           └──────────────────┘           └──────────────────┘
```

### 5.2 核心组件

| 组件 | 职责 |
|------|------|
| **Notification API** | 接收业务系统请求，校验参数，写入持久化存储，立即返回 202 Accepted。 |
| **Persistence Store** | 存储通知请求、幂等记录、vendor 配置、投递日志等。 |
| **Scheduler / Worker** | 定时扫描待投递记录，分配租约锁，调用 HTTP Client 投递，更新状态。 |
| **HTTP Client** | 根据 vendor 配置组装请求并发送，处理超时、响应码等。 |
| **DLQ Manager** | 管理死信通知，提供人工重放能力，触发告警。 |
| **Config Manager** | 管理 vendor 配置，支持运行时新增/修改配置而无需发版。 |
| **Monitor / Alert** | 记录 metrics、日志，队列堆积或 DLQ 新增时告警。 |

### 5.3 典型数据流

1. 业务系统调用 `POST /api/v1/notifications`，携带 `vendorKey`、`idempotencyKey`、`payload`。
2. 系统校验参数，检查幂等记录：
   - 若该 `vendorKey + idempotencyKey` 已存在且状态为 SUCCESS，直接返回原结果，不重复投递。
   - 若状态为 PENDING / FAILED，返回原请求 ID，不创建新通知。
   - 若状态为 DEAD_LETTERED，返回死信状态，不自动重试。
   - 若不存在，创建新的通知请求并持久化。
3. 返回 202 Accepted，告知业务系统“已接受，将异步投递”。
4. Scheduler 扫描状态为 PENDING 且到达投递/重试时间的记录。
5. Worker 获取租约锁，组装 vendor 请求（URL、Header、Body），通过 HTTP Client 发送。
6. 根据响应结果更新状态：
   - 成功 → SUCCESS
   - 可重试失败 → FAILED，计算下次重试时间，状态回到 PENDING
   - 不可重试失败 → 直接进 DLQ
   - 超过最大重试次数 → DEAD_LETTERED

## 6. 关键工程决策与取舍

### 6.1 投递语义：At-least-once

**决策**：采用 **at-least-once（至少一次）** 投递语义。

**原因**：
- 跨系统 HTTP 调用无法经济地保证 exactly-once；
- 业务方可通过幂等键和自身幂等设计来消化重复通知；
- at-least-once 在可靠性和实现复杂度之间取得了最佳平衡。

**代价**：存在极小概率的重复投递，需在文档中明确。

### 6.2 幂等设计

**决策**：由业务系统提供 `idempotencyKey`，本系统维护幂等记录的最终投递状态，并将同一 key 透传给 vendor。

**分层职责**：

| 层级 | 责任方 | 说明 |
|------|--------|------|
| 生成幂等键 | 业务系统 | 业务方最清楚“哪两个通知代表同一业务事件”。 |
| 本地去重 | 本系统 | 在保留窗口内，同一 `vendorKey + idempotencyKey` 只创建一次通知请求；已 SUCCESS 的不重复投递。 |
| 重试透传 | 本系统 | 同一条通知的所有重试使用同一 `idempotencyKey`。 |
| Vendor 去重 | Vendor | 本系统仅提供条件，不承诺 vendor 一定去重。 |

**DLQ 重复提交处理**：若原通知已进入 DLQ，业务方用同一 key 再次提交时，直接拒绝并返回死信状态，必须走人工重放 API。

### 6.3 重试策略

**决策**：采用**指数退避 + 抖动**的重试策略，并对错误进行分类。

- **可重试错误**：网络超时、连接失败、5xx、429（Rate Limited）。
- **不可重试错误**：4xx（除 429 外）、URL 非法、请求体格式错误等。
- **退避方式**：`nextDelay = min(base * 2^attempt + jitter, maxDelay)`，例如 1s → 2s → 4s → ... → 上限 1h。
- **最大重试次数**：设定上限（如 10~15 次），超过后进 DLQ。
- **429 特殊处理**：尊重 vendor 返回的 `Retry-After` 头。

### 6.4 死信队列（DLQ）

**决策**：超过最大重试次数的通知进入 DLQ，DLQ 支持人工重放和告警。

**DLQ 必备能力**：
- 按 vendor、错误原因聚合展示；
- 提供人工重放接口；
- 设定保留期，过期自动归档或删除；
- 新增死信时触发告警。

**取舍**：第一版 DLQ 可以是持久化存储中的一个状态，不引入独立的 MQ DLQ topic。

### 6.5 限流

**决策**：优先实现**按 vendor 的 outbound 限流**。

**原因**：
- 不同 vendor 容量差异大；
- vendor 故障时继续狂轰滥炸会加剧问题，甚至被封 IP；
- 限流本质上也是一种降级手段——桶空时新通知仍被接受，只是投递被延迟。

 inbound 限流可在后续根据实际流量压力补充。

### 6.6 降级与熔断

**决策**：引入简单熔断机制。

- 当某 vendor 连续失败率达到阈值（如 50% / 最近 10 次）时，打开熔断；
- 熔断期间，该 vendor 的新通知仍被接受并持久化，但 worker 不立即投递，而是等待熔断恢复期后再试；
- 熔断帮助节省线程、连接和 DB 资源。

**取舍**：第一版使用内存级熔断状态即可；分布式熔断状态共享是后续演进项。

### 6.7 并发控制

**决策**：采用**租约锁（Lease Lock）**机制。

每条待投递记录维护 `locked_by` 和 `locked_until` 字段：
- Worker 只选择 `locked_until < now` 的记录；
- 处理前更新 `locked_until = now + leaseDuration`；
- 锁超时时间略大于 HTTP 超时 + 处理时间（如 HTTP 30s，锁 60s）。

**优势**：
- 多 worker / 多实例不抢同一条记录；
- worker 崩溃后锁自然过期，其他 worker 可接管，无需额外心跳检测。

### 6.8 崩溃与重启恢复

**决策**：完全依赖持久化和租约过期来实现恢复。

- 所有通知请求写持久化存储，服务崩溃不丢数据；
- 重启后，scheduler 扫描 `PENDING` 或 `FAILED` 且 `nextRetryAt <= now` 的记录；
- 处理中状态（SENDING/PROCESSING）的记录，因租约过期后会被重新 pickup；
- 幂等机制保证重复 pickup 不会导致业务问题。

### 6.9 告警

**决策**：告警异步触发，不阻塞主流程。

需要告警的场景：
- 通知进入 DLQ；
- 某 vendor 连续失败率超过阈值；
- 队列堆积超过阈值。

**取舍**：第一版可先通过日志 + 简单告警接口实现，后续接入 Slack/邮件/PagerDuty。

### 6.10 快速接入新第三方

**决策**：Vendor 配置完全数据化，新增 vendor 无需发版。

每个 vendor 一份配置，包含：
- 基础信息：`vendorKey`、endpoint、HTTP method、timeout；
- 请求模板：headers、body template；
- 投递策略：重试次数、退避参数；
- 限流参数：QPS；
- 幂等键位置：Header 或 Body 中的字段名。

业务方只需通过 `vendorKey` 调用，系统按配置自动组装请求。

### 6.11 DB 队列 vs 消息队列

**决策**：MVP 采用 **DB 队列 + Scheduler 拉取** 模式，而非 Kafka/RabbitMQ。

**原因**：
- DB 队列足以满足 MVP 的可靠性和吞吐要求；
- 减少外部依赖，降低部署和运维成本；
- 状态机、幂等、重试调度天然适合关系型存储表达。

**替代方案**：当流量或延迟要求显著提升后，可演进为 MQ（如 Kafka/RabbitMQ）+ 消费者模式，DB 仅保留幂等和状态查询。

## 7. 可靠性与失败处理策略

| 失败场景 | 处理策略 |
|---------|---------|
| 网络超时 / 连接失败 | 标记为可重试，按指数退避调度下次重试。 |
| Vendor 返回 5xx | 可重试，纳入重试调度。 |
| Vendor 返回 429 | 可重试，优先尊重 `Retry-After`，否则按退避策略。 |
| Vendor 返回 4xx（除 429） | 不可重试，直接进 DLQ。 |
| Vendor 长期不可用 | 熔断打开，新通知暂存不投递，恢复期后自动重试。 |
| Worker 崩溃 | 租约锁过期后，其他 worker 接管。 |
| 服务重启 | Scheduler 自动恢复 PENDING / FAILED 记录。 |
| 超过最大重试次数 | 进入 DLQ，触发告警，等待人工重放。 |
| 重复提交（已 SUCCESS） | 直接返回原结果，不重复投递。 |
| 重复提交（已在 DLQ） | 拒绝并返回死信状态，要求走人工重放。 |

## 8. 取舍与演进

### 8.1 哪些设计是“过度的”，第一版不采纳

| 过度设计 | 不采纳原因 | 后续演进触发条件 |
|---------|-----------|----------------|
| Kafka / RabbitMQ | MVP 流量和复杂度不需要，DB 队列足够。 | 吞吐量达到 DB 轮询瓶颈，或延迟要求 < 100ms。 |
| 分布式熔断状态 | 多实例间共享熔断状态实现复杂，第一版单实例内存熔断即可。 | 部署多个实例且需要全局熔断视图。 |
| 企业级 KMS / Vault | 密钥管理是独立领域，第一版简单配置即可。 | 安全审计要求或密钥轮换需求。 |
| Exactly-once 投递 | 跨系统 HTTP 下成本过高，收益不明确。 | 业务方明确要求且愿意承担 vendor 改造成本。 |
| 复杂规则引擎渲染 Body | 模板替换足够覆盖当前 vendor 差异。 | vendor 请求格式需要动态计算、条件分支等。 |

### 8.2 未来演进方向

1. **消息队列化**：当流量增长时，将 DB 队列替换为 Kafka/RabbitMQ，DB 保留幂等和查询能力。
2. **独立 DLQ 存储**：将 DLQ 从状态升级为独立 topic/表，支持更灵活的审计和重放策略。
3. **多实例协调**：引入分布式锁或全局熔断状态。
4. **密钥管理**：接入 Vault / AWS Secrets Manager 等。
5. **可视化运维**：提供管理后台，查看通知状态、DLQ、vendor 配置等。
6. **优先级队列**：为不同业务事件设置投递优先级。
